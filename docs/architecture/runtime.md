# Runtime

Status: implemented (2026-10-25). Numbers are starting defaults to be validated by the measurements in
`quality-attributes.md`; change them there and here together.

## Critical path: request in the app → visible on the map

1. The app handles a request. The SDK records spans in memory; nothing blocks the request path on export. The Rust
   SDK's server span ends when the response body has been sent (or dropped), with the captured bodies attached.
2. The SDK batch processor exports every 500 ms (OpenTelemetry's default is 5 s, too slow for a live map) or when
   512 spans are queued, 64 in the web SDK: a failed export there retries its whole batch on the page's main thread
   (`quality-attributes.md`, runs H and I). Shutdown flushes the whole queue at once, so the web exporters allow
   33 concurrent exports (a full queue of 64-span batches), below the collector's 64.
3. `POST /v1/traces` → body limit → decode (protobuf or JSON) → normalize names → redact → store (and add one log
   line per stored span) → link and update graph → publish SSE events (`node`, `edge`, `request`, `log`) → respond
   `200`. All in one handler; no internal queue.
4. The UI applies `node` and `edge` events on the next animation frame, so counters update at once. A request's
   spans come from several processes in separate batches, each producing a `request` event; the UI animates the
   request once, 300 ms after its last event when its root span has arrived (`has_root`), else 1.2 s after it.
   Hops are placed along the call tree: a hop called inside another hop's server span is offset from that server
   span in its own clock, never by comparing clocks of different processes.

Target: p95 ≤ 2 s from request end to the map on a local machine (`quality-attributes.md`).

## Outbound calls and gRPC

The client Tower layer starts one span at `call`, injects its context, and delegates readiness to the same inner
service instance. It adds no connection, retry, deadline, queue, task or concurrency limit: these remain the
application transport's responsibility. Completion follows the response body, including gRPC trailers. Transport or
body failure records a fixed error category; cancellation ends the span without waiting for export. Streaming body
polls run in the span context so nested work remains correlated. State is per call; there is no shared active span.
Capture uses the existing per-body bounds and exporter queues. Caches, persistence and additional services are not
needed for this instrumentation. See ADR-0015 for compatibility and capture limits.

## App logs and actions

Both SDKs batch logs separately from spans with the same 500 ms interval, batch size (512, web 64), 2,048-record queue
and 2 s export timeout. Shutdown shares a 2 s budget across both pipelines. The Rust tracing bridge masks fields and
JSON text before enqueueing; at most 64 fields and a 12 KiB content budget, with 2 KiB per text/debug field. An
oversized field is replaced whole so a cut JSON prefix cannot leak a sensitive key's value.

The browser console serializer visits at most 128 values, six nesting levels, 32 keys per object and 16 arguments,
with a 12,000-character working budget and about 12 KiB of UTF-8 output. Action capture queues at most 128 pending
events, with accessible names capped at 128 characters, element descriptions at 256 (64 per attribute value) and
navigation paths at 512; an event is stamped with its own time and emitted on the next timer turn, after synchronous
handlers have had a chance to link their fetches.
Export transport diagnostics are excluded to avoid feedback loops (`interfaces.md`).

`POST /v1/logs` shares trace ingest admission, CORS, body and timeout bounds. Decode and recursive redaction run
before the store lock; a record is then bounded, stored and published as `log`, and its service as `node` when
changed. No request/edge events are generated by logs. Edge filtering resolves optional context against retained
spans at query time, so batch arrival order does not determine correlation.

## Linking spans into edges

- A server span whose parent is a client span from another service creates or updates the edge
  `client.service → server.service`.
- A client span with a database system attribute creates or updates `service → database node` at once.
- A client HTTP span whose server child has not arrived waits in the pending map for the link window (10 s). After
  that it is counted on `service → external node` (`ext:<server.address>:<server.port>`). A server child that arrives
  later still links future requests, but counts already given to the external node stay there.
- Spans can arrive in any order (child before parent, browser batch after backend batch); linking checks both
  directions on arrival: a server span whose client parent has not arrived waits in its own bounded map for the same
  window, then is dropped.

## Bounds

Every buffer is bounded; on overflow the oldest entry is dropped and ingest is never blocked.

| Resource | Default bound | On overflow |
|---|---|---|
| OTLP request body | 4 MiB | `413` |
| Concurrent ingest requests | 64 | `503` + `Retry-After: 1` |
| Stored requests | 10,000 and 256 MiB of span data | Evict the oldest request |
| Spans per request | 1,000 | Drop further spans, count them in `dropped_spans` |
| Events per span | 32 | Drop further events, add `events` to the span's truncated keys |
| Log entries (span lines and app/action records) | 50,000 and 64 MiB of entry data | Drop the oldest by time |
| One app/action log record after redaction | 16 KiB of body, attributes and service data, at most 64 attributes | Shorten text and discard excess attributes, mark truncation |
| Routes per edge | 16 | Count further calls under `(other routes)` |
| `GET /api/logs` page | 100 by default, at most 500 | Clamp `limit` |
| Activities (ADR-0016) | 10,000 | Drop the oldest by time |
| Traces listed per activity | 64 | Further traces still join the action, counted in `traces_unlisted` |
| Steps of one activity | 1,000 | Leave out the rest, counted in `truncated_steps` |
| `GET /api/activities` page | 50 by default, at most 200 | Clamp `limit` |
| Attribute value length (collector side) | 256 KiB | Cut, mark as truncated on the span or event; HTTP bodies cut here are masked whole (`security.md`) |
| Pending client spans | 10,000 | Oldest is attributed to its external node now |
| Server spans waiting for their client parent | 10,000 | Drop the oldest |
| Nodes / edges | 1,000 / 5,000 | Ignore new ones, log a warning once per minute |
| SSE clients | 16 | `503` for the 17th |
| SSE broadcast buffer | 4,096 events | Lagging client gets `resync` |
| SDK export queues (both SDKs) | 2,048 spans and 2,048 logs separately | Drop new records, the app is not affected |

## Timeouts and retries

| Operation | Timeout | Retry |
|---|---|---|
| SDK export (HTTP POST) | 2 s | chepio-lens adds no retries; any built-in exporter retry on `429`/`503` must fit in the timeout (verify per SDK), then the batch is dropped. Rust SDK: opentelemetry-otlp 0.33 without its experimental retry feature, so no retries. Web SDK: the OpenTelemetry JS exporter retries `429`/`502`/`503`/`504` and network errors with backoff, but never past the 2 s deadline |
| Collector reading a request body | 10 s, then `408` | — |
| Graceful shutdown | 5 s to finish in-flight ingest and close SSE streams | — |
| UI SSE reconnect | browser `EventSource` default, then refetch `/api/graph` | Automatic |

## UI activity window

The logs panel opens on actions (ADR-0016) and remembers the view. The actions view loads 200 activities per page and
keeps at most 500, oldest first by cursor; SSE `activity` invalidates like `log` does, an activity named in `replaces`
leaves at once, and an expanded activity reloads its steps on every update of it. Only the shown view loads.
The lines view loads 500 lines per page and keeps at most 2,000, sorted by timestamp and arrival sequence. Live
refreshes follow SSE invalidations coalesced over 250 ms; an active refresh can catch up through at most four pages.
There is no polling while idle or while the panel is closed. Loading earlier lines keeps the older end of the
window and pauses live updates; resuming replaces it with the newest page. Scrolling upward pauses automatic
updates, and reconnect/resync preserves a paused reading window until the reader resumes. Filter changes cancel
previous requests. A missing/evicted request is explained in the inspector; failed loads can be retried.

## Failure behavior

| Failure | What the user sees | Behavior |
|---|---|---|
| Collector not running | App works normally; map is empty | SDK export fails fast, batch dropped |
| Collector overloaded | Some requests missing on the map | `503` from ingest, SDK drops after its retry |
| Malformed OTLP | Missing spans | `400`, warning logged at most once per minute per source |
| Browser blocked by CORS | No frontend node; backend still visible | Collector answers `403` and logs the rejected origin at most once per minute; documented in the connection guide |
| Missing `traceparent` on backend calls | Frontend and backend appear unlinked | Frontend client spans go to an external node after the link window |
| Clock skew between browser and server | Waterfall offsets look wrong | Durations are always per span; the UI marks a child that starts before its parent |
| Store full | Old requests disappear from the list | Graph totals are kept |
| UI tab falls behind | Brief jump of the map | `resync` → fresh snapshot |

## Concurrency model

- Tokio multi-threaded runtime. Store and graph sit behind one `std::sync::Mutex`, held only for in-memory updates
  and never across `.await`. Revisit if lock wait shows up in profiles (`quality-attributes.md`).
- Decoding protobuf or JSON happens before taking the lock.
- SSE uses `tokio::sync::broadcast`; a lagged receiver maps to the `resync` event.

## Collector self-observability

- Structured logs to stderr with no payload values.
- `GET /healthz` on the UI listener.
- Counters exposed in `GET /api/stats`: spans received, dropped (by reason), requests evicted, pending links,
  SSE clients; logs received/rejected, retained log entries/bytes, logs evicted; activities and activities evicted.
  Byte counts estimate retained data,
  not process RSS. Reset clears storage and graph; ingest counters remain cumulative and store eviction counters reset.
